# Skyrim MOD 汉化发布

发布物料和翻译物料是两种东西。翻译面向译者和审校，讲证据、讲裁决、讲批次；发布面向玩家，讲这 MOD 是什么、装了会怎样、怎么装。把内部口径搬进发布帖，玩家读不懂；把玩家的期待搬进翻译流程，条目会说不清。

本 skill 管前者：把已收口的汉化变成一整套能发出去的东西。它给的是判断方法，不是某一次发布的模板——题材、术语、样式都随 MOD 变，变不了的是核对口径和合成边界。

## 1. 三段流程与顺序

**先文案，后封面，最后合成。** 文案定下来才知道封面要不要留标题位、标题写几个字。反过来做，图上先压了字，文案一改就得重做。

1. **写发布文案** → `RELEASE.md`，落 `mods/<plugin>/`
2. **生成封面底图** → 无文字、无国旗的纯画面
3. **底图交独立复核** → 美术与审美，另一个 agent 看
4. **合成标题与国旗** → 用 `scripts/compose_cover.ps1` 后期叠加

第 2 、4 步必须分开，因为分工不同：图像模型擅长画质感与光影，不擅长写准确的汉字。底图交给模型，文字交给合成，各自做各自擅长的。第 3 步不能省，理由见 §6.5。

## 2. 文案：结构

玩家打开帖子只有两个问题：这是什么，怎么装。围绕这两个问题铺六节，顺序固定：

1. **这个 MOD 是什么** —— 用玩家能在游戏里想象到的具体场景讲
2. **这份汉化覆盖什么** —— 条数、插件数、覆盖了哪些子 MOD
3. **怎么装** —— 分步写，玩家能照着做
4. **译名怎么定的** —— 举几个容易译错的例子，给依据
5. **一点说明** —— 提前解释容易被误读成翻译问题的地方
6. **反馈** —— 告诉玩家怎么报问题、带什么信息

## 3. 文案：事实核对

发布文案的每句话都会被玩家拿到游戏里对照。错误分两类：一类是数字和名称写错，玩家一装就发现；一类是表述把范围写窄了，读起来像漏了什么。两类都靠同一套办法防——**写之前回到源头，不凭借记忆和二手文档**。

### 数字必须现场统计

项目文档里的统计是写它那一刻的数。之后条目可能增删，当初也可能算错，更常见的是文档统计口径与玩家实际看到的不同（比如主插件条目数与含补丁的条目总数）。

写文案前跑一遍实际统计，以输出为准。文案里的每个数字都应当能指向某一次命令的结果。文档只用来找线索，不用来抄数字。

### 名称必须回源核对

插件名、MOD 名、NPC 名，逐条对照源 XML 的 `<Params>` 与实际文件名。拼错一个字母，玩家就会搜不到或者装错。

### 译名举例必须能从 canonical 里 grep 到

文案里想举「他们管某某叫某某」来说明译名取舍时，先 grep 一遍实际译文，确认举的形与库内逐字一致。

举例子最容易出的错是凭印象写：脑子里记得某个词的译法，写下来的却是另一个形。读者里有同时看过正文和简介的，两处不一致就是自相矛盾的证据，会让人怀疑整份汉化的可靠性。一个 `grep` 能避免。

### 对象范围按实际清单写，不按直觉写

发布帖里描述「这个世界里有哪些东西被覆盖」时，先把实际清单归一次类，再决定用什么词。

直觉会默认对象都是人，一旦 MOD 覆盖了非人对象（家族、组织、地点、生物、事件），写「人物」「角色」就把它们排除在外了；反过来写「你」，则假定读者就是游戏里的那个受文者，而档案类 MOD 的对象是 NPC，不是玩家。

归类本身只要一次统计，写错却要读者来信指正。

### 数量关系要自洽

一个对象可能对应多条记录。写「各一份」之前先确认没有多卷的情况——同一段里前面说「各一份」、后面说「写了整整五卷」，两句话互相打脸。

### 装法只写验证过的

分插件导入还是给成品文件，取决于实际交付形态。菜单名、文件层级、是否需要工具，凡是没亲手验证过的都不要写死。

多插件 MOD 通常要说明各插件分开处理，并给出原因（每个插件的参数指向不同目标文件，合并会导致写回错位）——原因是给玩家的可信度，也是他遇到问题时的判断依据。

### 没有的信息留空，没有的成就不吹

版本号、作者、发布日期手上没有就不写，编一个比留空糟得多，发布时由发布者补。

「完美汉化」「零错误」「业界最强」这类无法验证的说法一律不写：写了就要被举证，而举证成本远高于一开始就不说。

### 写作用语

遵循 `shuo-ren-hua`：日常词、完整句子、少破折号、冒号只引列表、不堆排比、不打比方。发布文案最常见的三种腔调是「不只是 X 更是 Y」「赋能 / 打造 / 致力于」「三连短句排比」，出现即改。

## 4. 文案：独立审查与驳回

写完派一个子代理审，权限为可写，写盘范围限定在它的报告路径。任务卡里给三类检查点，并**先自己把权威数字统计好写进卡里**——不写给它，它会去数文档，而文档正是可能过时的那个来源。

三类检查点：

- **事实错误**：数字、插件名、MOD 名、译名举例，与任务卡给的权威数字或术语表不符
- **表述失准**：对象范围、安装方式、数量关系与实际有出入
- **夸大误导**：把没做到的说成做到了

**审查结论必须回源验证，不能直接采信。** 审查者看的也是二手材料，它可能：

- 拿术语表反推，把 canonical 里正确的形判成该改（术语表与 canonical 冲突时，canonical 与官方词典为准）
- 把「不属于该集合的额外条目」算进集合，得出数量差一的结论
- 凭记忆写外文名，多打或少打一个字母，再据此指控拼写错误

核实方法很机械：数字回统计，译名回 canonical 与官方词典，条目数回 XML 清单。**按证据改，不跟报告给的理由走**——结论对、理由错的情况很常见，改错了方向比不改更糟。

驳回的理由写进 `PROGRESS.md` 的审查记录，避免下一轮重复排查同一处。

## 5. 封面底图

### 先找视觉锚点，再写 prompt

**不要查看、比对或参考项目里和媒体库里的任何一张已有封面图。** 不看是硬要求，不是风格建议。锚点一旦进入视野，构图类型、光位方向、留白位置就会被默认沿用，连「要避免像它」的意图也挡不住——判断基准已经被换掉了，接下来只是给那张图换道具。锚点只从当前 MOD 的源材料取：术语表、剧情上下文、任务日志，以及原文里反复出现的物件与场景。

封面的任务是让玩家在缩略图大小下认出「这是哪个 MOD」。锚点来自 MOD 本身，不是通用审美，通常两到四个即可：

1. **题材的核心物件** —— 这 MOD 讲的事，玩家在游戏里会碰到的那个东西
2. **可辨识的机构或派系标识** —— 有标识就用标识，它比场景更快被认出
3. **材质与工艺** —— 这东西是什么做的，金属、纸、石、布，质感是可信度的来源
4. **一处能读出「刚使用过」的细节** —— 笔迹、余温、磨损，让画面不是静物陈列

锚点确定后，把它拆成可解析的描述：材质层级、表面缺陷、摆放关系。评价词（精美、有氛围、高级）不产生画面，一律换成手段。

### 光、镜头、构图

固定的三段写法：

- **光**：主光给方向与色温（如「左上四十度冷白窗光」），辅光给位置与强度（如「右侧深处一点弱暖光」），再交代冷暖交界落在哪里
- **镜头**：焦平面锁在锚点物件上，前景和背景分别怎么虚化，各自留下什么颜色
- **留白**：标题要压在画面某处，prompt 里点明那块区域是暗部空地，否则模型会填满细节

比例用 16:9，适配主流发布平台的封面位。

### 约束两侧都写

必须保留什么（锚点物件清晰可辨）、不得出现什么（可读文字、水印、重复物件）。只写一侧等于没约束——模型不会因为没有禁止就避开。

### 底图不写字

**不要试图让图像模型写标题、标签或任何可读文字。** 汉字笔画多，模型会写出结构错误或形似的假字，缩到缩略图尺寸后仍然看得出歪。

底图只出画面，所有文字在第 3 步合成。

## 6. 底图：独立复核

底图生成后先交另一个 agent 复核美术与审美，不要自己看完就合成。生成者对自己写过的 prompt 有确认偏差，看得出「像不像我描述的」，看不出「作为封面成不成立」。

复核者的选取：不得是生成本图的一方；不得预先查看此前的封面图（同 §5 的理由，参照一旦建立，评审也会跟着滑向那张配方）；不要求它懂这个 MOD 的设定，要求它按观众的第一眼判断。

检查点分两类，先给客观项：

- **客观项**：画面里有没有可读文字、字母、数字、水印；有没有人手、人脸、多余或重复的物件；建筑透视与物件支撑关系有没有穿帮；锚点物件是否清楚可辨；预留的暗部空区是否真的空且够宽。
- **审美项**：缩略图可辨性（想象把图缩到两百多像素宽，还能不能认出题材）、主体与留白的力量分配、光影是否服务于主体、气质是否与 MOD 题材相符。

输出：通过或不通过，附逐条问题与位置。不通过的处置是**重写 prompt 重生**，不是调几个词碰运气；客观项不通过一律不合成。

裁决口径：客观项按证据判，审美项采纳复核者结论。复核者说「不够好」但指不出具体位置时，要求它指出再决定，不接受笼统评价。

## 7. 合成标题与国旗

用 `scripts/compose_cover.ps1`。Windows 自带 System.Drawing，不需要装 PIL。

```powershell
.\scripts\compose_cover.ps1 `
  -Cover '.\cover-raw.png' `
  -Flag  '.\Flag_of_the_People''s_Republic_of_China.png' `
  -Title '简体中文汉化' -Subtitle '<MOD 英文名>'
```

省略 `-Out` 时输出 `<原图名>-cn.png` 到同目录。参数全部可在命令行覆盖：字号、国旗宽度、内边距、字体、主副标题。

### 国旗是标准件，禁止手绘

五角星有严格的几何规范（大星的星角朝向、四颗小星各有一角对准大星中心）。这些关系无法凭肉眼坐标还原，缩到几十像素高之后必然失真，而读者的辨识基准是天天见到的那面旗。

正确做法：

1. 取得标准国旗图片（发布者提供的，或公版素材），比例 3:2
2. 脚本只做等比缩放，插值用 HighQualityBicubic
3. 脚本会校验比例，不是 3:2 直接报错退出 —— **不裁剪、不拉伸**，换图

同理适用于任何有官方规范的标识：机构徽章、评级标志、平台 logo，都取标准件缩放，不重绘。

宽度默认 60px。在 1200 像素宽量级的画布上约占 5%，既能被认出又不抢画面。想让星更清楚可以放到 72 或 80，代价是比主标题高出一截。

### 参数默认值与其依据

| 参数 | 默认 | 依据 |
| --- | --- | --- |
| `-TitleFont` | `STZhongsong` | 中宋带笔锋，落在复古、材质感强的画面上不违和。若题材是现代或赛博，改无衬线；判断标准是画面本身有没有笔触感 |
| `-TitleSize` | 44 | 在 1200 像素宽画布上约占画面宽度的 3.5%，视觉重量与副标题形成两级。画布更宽时按比例上调 |
| 标题色 | `#F4EAD6` 米白 | 比纯白暖一档，落在深色背景上像印上去的，纯白会显得是贴图 |
| 副标题色 | `#CEB07A` 暗金 | 与主标题形成明度差，不抢读序；换成画面里已有的点缀色同样成立 |
| 阴影 | 半透明黑，偏移 2px | 没有它，浅色字压在木纹、布料、纸面上边界会发虚 |
| 底部渐变 | 62% 高度起，到 120/255 | 底图底部常是亮的或纹理密的，白字直接压上去会糊。渐变很缓，看不出是后加的 |

位置：标题与国旗整体右对齐到 `画布宽 - 内边距`，国旗在标题右侧，间隔 18px，形成「旗 + 字」的单一视觉块。读者先看到字，再看到旗。

## 8. 验收清单

发布前逐条过：

- [ ] 文案里的每个数字都来自本次统计输出，不是抄文档
- [ ] 插件名、MOD 名逐条对照源文件，无遗漏无拼错
- [ ] 每个译名举例都在 canonical 里 grep 得到同一个形
- [ ] 对象范围按实际清单归类，没有默认「都是人」
- [ ] 数量关系自洽，没有「各一份」与「好几卷」并存
- [ ] 装法的每一步都实际成立，菜单名没有编造
- [ ] 没有版本号、作者、日期等手上没有的信息
- [ ] 没有无法验证的绝对化说法
- [ ] 独立审查跑过，每条发现都回源验证过，驳回理由已记录
- [ ] 没有查看过此前的封面产物（并确认复核者也没看）
- [ ] 封面底图经独立复核通过，客观项零问题
- [ ] 封面底图无任何可读文字与国旗
- [ ] 国旗、徽章等规范标识是标准件等比缩放的，不是绘制的
- [ ] 标题字在成图上没有糊边、没有压到画面主体

## 9. 已知故障形态

| 现象 | 成因 | 处置 |
| --- | --- | --- |
| 封面上的中文是错字或假字 | 交给图像模型写中文 | 底图不写字，全部后期合成 |
| 规范标识看着「像」但不对 | 凭坐标重绘 | 用标准件图，脚本只做等比缩放 |
| 标识边缘发毛 | 插值用了默认的双线性 | 用 HighQualityBicubic |
| 文案数字与文档一致但与实际不符 | 抄了项目文档 | 现场统计，文档只当线索 |
| 审查报告把对的判成错的 | 审查者拿二手依据推断 | 每条回源：数字回统计、译名回词典与 canonical |
| 标题压上去看不清 | 底色亮且无遮罩 | 保留底部渐变压暗 |
| **不同 MOD 的封面越长越像** | **看过此前的封面，构图与光位被沿用** | **不查看已有封面（§5）；底图交独立复核（§6）** |
| 换个 MOD 就用不了这份 skill | 把某次发布的题材与术语写成了规矩 | 留核对方法，不留具体结论 |
