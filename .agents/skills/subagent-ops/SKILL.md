# 子代理协作操作

本文写给**编排者**（主代理 / 主会话 / orchestrator）。委派把独立可并行的工作移出主上下文、交给多个执行者，代价是引入一类新的故障面：任务卡设计错误、体量失控、写冲突、验收漏检、故障误归因。以下纪律按出错代价组织，每条对应一种已识别的故障模式与防御动作。

与其他项目文档冲突之处，以项目自身的规范为准。

## 1. 核心模型与能力假设

委派对环境的依赖如下；缺失项按降级列执行。

| 能力       | 典型形态                                       | 缺失时的降级                                   |
| ---------- | ---------------------------------------------- | ---------------------------------------------- |
| 可续接实例 | 创建返回句柄；可向同一实例追加任务并保留上下文 | 每次新建实例，把上一轮的必要上下文写进新任务卡 |
| 实例池可见 | 可查询在途 / 空闲实例与最近活动                | 按固定并发上限自行控制，关闭动作本地记账       |
| 结果通知   | 实例完成时编排者收到结果                       | 手动收尾收集产物，核对完成条件                 |
| 权限分级   | 只读 / 可写等权限档位                          | 无分级时，用任务卡显式约束可写范围             |
| 后台并行   | 派单后编排者继续本轮工作                       | 无法并行时退化为串行委派                       |

三条底层事实：

- **产出由权限决定**：任务卡里写明的每个产出通道，必须是该实例真实可用的工具。
- **编排者是唯一记得全局的角色**：子代理只见任务卡与输入文件。不给的信息它不知道，给错的信息它会当真。
- **上下文会稀释**：实例携带的无关历史越多，注意力越差。体量与续派次数都受此约束。

## 2. 委派决策

适合委派：

- 独立可并行的批量工作（批量转换、审计、调研、扫描）；
- 需要独立视角的复核；
- 深水工作：细节沉在子代理，只回摘要与产物，保护主上下文。

不适合：编排者一步能完成的读写与查询；需要即时往返澄清的对话。

判断句：一件工作如果可以被写成一个自包含的任务卡（输入、输出、完成条件都明确），就是委派候选；写不清楚就先写卡，再决定派给谁。

### 发现与裁决分离

大搜索空间任务（找漂移、找遗漏、找异常）遵循以下模式：

- **发现器只做模式识别**：不携带白名单、不预知正确答案。给白名单会诱导它对表内项放松警惕；预告正确形态会让它变成橡皮图章，只确认预期。
- **裁决由编排者执行**：对照规范、语境与证据判定。发现器的输出永远是结构化候选清单（候选 + 出现位置 + 依据），不是结论。
- **局部发现，全量核对**：候选在局部（分块）发现；核对必须覆盖全部出现位置。
- **机械比对不消耗子代理**：能靠逐行比对、集合运算解决的事情交给确定性脚本；子代理留给需要模式识别与判断的部分。

发现器的任务卡要点（以名词收敛的种子扩散为例）：输入按语义区域分块（每实例 ≤500 行，字段显式、多行排版）；从源文找专名种子（人名/地名/组织/派系/神名），排除句首普通词（问候动词、句首大写词）与纯普通名词；产出契约 `{english, zh_forms: {形态: [idx...]}, sample}`，只报 ≥2 种中文形态的候选。种子在块内发现、对全文核对——块负责发现，全文负责核对，不是块内自比。权限与输出通道匹配：只读实例把结构化产出完整贴在报告里，由编排者落盘；任务卡里不下脚本指令。

## 3. 执行者选型与权限契约

### 选型：生产求同，审查求异

- **并行生产**：同一 agent / 同一模型的多实例。共享同一套指令与词表，产物一致性最好。
- **独立审查**：换模型或至少换全新实例，且与被审产出的生产上下文隔离。审查者只看最终产物与检查标准，只产问题清单，不直接改产物；修正由编排者统一执行。
- **专长匹配**：按任务性质分派。语言感觉强的处理口吻与文体，结构化强的做审计与机制分析，敏感数据限定在可控环境内处理。
- **廉价 worker 的边界**：模板化、低风险、结构简单的内容可以交给成本最低的执行者（含本地模型）；复杂语义、角色语气、术语敏感内容不交给它，返工成本高于节省的成本。

### 权限与输出契约三角（派单前必查）

- 只读实例通常不能写文件、不能执行命令，且提权重试不会改变结果。给只读实例写「保存到路径 X」的输出契约会让任务卡住或产出无人接收。只读实例的正确输出通道：把结构化产出完整附在最终报告里，由编排者落盘。
- 可写实例才可以在任务卡里指定写盘路径，同时约束写盘范围。
- 需要执行命令的任务（跑校验、跑转换）必须派给可执行命令的权限档位。
- 三角必须自洽：**输出指令 ↔ 权限 ↔ 实际可用工具**。不一致即派单错误。

### 输入预切格式

- 数据在派单前预切成低耗读取的结构：一行一条、字段显式、多行排版。单行超长的数据会堵死逐行读取路径，把子代理逼进「跑一段脚本、看一眼输出、再写一段」的循环。
- 探索与内容类任务，用结构化输入替代命令式指令；任务卡只给读取、检索、写入路径，以及必要的格式约定。

**证据预切（查询型知识预编译）**：术语命中与语境锚点在派单前由确定性工具压成一屏摘要（每键数行），任务卡输入段指向摘要、不指向原始上下文——原始上下文常达 95–105 KB，超单次读取上限，执行者会绕道 shell 逐词查证，把实例预算耗在机械查询上。摘要由编排者用确定性工具生成，执行者只读不查；摘要的缺项照列「-」，让执行者知道「没有」是真的，不是漏看。

## 4. 任务卡编译（信息三分法）

子代理收到的不是整套规范，而是编排者编译出的一张**任务卡**。规范是源代码，编排者是编译器，执行者只拿到当前任务的最小执行路径。决定成败的变量不是 token 数，而是**决策节点数**：

> 信息少到一定程度，模型开始补全世界；信息多到一定程度，模型把任务本身当成研究对象。

据此把信息分三类管理：

1. **执行路径**（进注意力核心，只留最小闭环）：输入在哪、输出到哪、输出格式、契约字段、一个硬校验、遇到未知项怎么处理。
2. **查询型知识**（不让模型背，让模型查）：术语、专名、规则放进落盘文件；任务卡只写「以某文件为准；本批命中见某上下文文件；仍查不到则标 WAITING / 待定」。
3. **验收知识**（不交给执行者）：失败模式清单、禁词扫描、对账规则属于编排者与门禁侧。执行者只需要知道怎样成功，不需要知道全部怎样失败。把整个失败空间告诉模型，它就开始搜索失败空间。

### 任务卡模板

```text
任务：<任务名与范围，如：翻译 INFO-<bid>；审计 <批组>>

输入：
- <键文件>（键的唯一来源，逐行复制）
- <工作单>（数据与待填字段；不含术语信息）
- <证据摘要>（本批已预切的术语命中与语境锚点；不要读原始上下文文件）
- <词表 / 规范文件>（专名与术语以它为准）

契约：
- 专名以 <词表文件> 为准，原样采用
- 每个键必须有一个输出
- 未确定项标 REVIEW，不自行定稿（合法枚举从执行器源码核出；本项目为 TRANSLATED / REVIEW / KEEP，无 WAITING）
- <文体与语言的一句话，如：自然口语中文、奇幻语境，避免现代词与翻译腔>

输出：
- path: <输出路径>
- 落盘：必须把产出实际写入 path 指定的文件，写入后读回确认；只在报告里贴 JSON 不算产出
- schema: <精确格式，逐字段说明>

完成条件：
set(output.keys) == set(input.keys)
```

模板末尾固定附三句（不属契约段，不占契约条目）：

1. `执行范围：只做「读输入 → 写输出 → 交卷」三件事。不查找或研究本卡未列出的工具、技能文档与后续流程（验收、门禁、写回由主会话执行）；不做任务之外的检查与验证。写完立即交卷；若接近时限仍未完成，把已完成部分落盘交卷，宁可交不完美不交零。`
2. `不编写任何脚本、不创建临时文件（含内联命令）：核对要点用文件读取与内容检索等只读方式直接完成；键集比对、去重检查、跨批对齐等机械校验一律由主会话统一执行。`
3. `生成纪律：不在思考里预演整批产出、不复述术语清单（证据看摘要，直接落笔）；不自我验证、不自我修复——写完就交卷，发现的问题（错字/引号/存疑条目）一律写进报告，由主会话处理。`

三句的作用：① 范围句防执行者自发研究交付链路（找验收工具、读下游文档、研究下游用法），把实例预算耗在卡外动作上；② 禁令句从通道上杜绝「脚本繁殖」——本可用只读工具完成的核对会演化成逐段写脚本，并随批次向后续执行者扩散；③ 生成纪律句防生成被中途截断：预演整批、复述清单、收尾自我修复是截断高发的三类行为，收尾越短越稳，把问题写进报告是最便宜的出口。

较长任务可用五段式展开：**背景（必读）→ 输入 → 产出契约 → 输出 → 报告格式**。报告要求结构化：状态（DONE / BLOCKED）+ 关键数字 + 不确定清单；拒绝散文式长汇报。不设自检段（见模板红线）。

### 模板红线（违反即重写）

- **不枚举禁词**。枚举禁令诱导执行者专注「别踩线」，产出形近错误（记得红线，忘掉正确形态）；自检也随之退化为「证明没踩线」。正确做法是引导查证：以词表为准、查到照用、查不到标 REVIEW。禁词只保留「出现即事故」级的一句话（如平台污染词）；泛禁形与术语禁形是门禁与验收侧的事，不进任务卡。
- **契约文案真实性**。任务卡里所有「什么文件、什么字段、什么是契约」的陈述，发出前必须打开真实文件核验。字段不存在时，执行者要么卡住，要么脑补「契约内容」；幻觉授权比不写更危险。
- **术语只走两条通路**：落盘词表 + 任务上下文文件的检索字段。新裁决先落盘再派单；任务卡内零术语清单。
- **复制制**。派单文本从模板逐字复制后填空，不凭记忆重组；凭记忆重写是契约文案缺陷的主要来源。
- **自查动作**：发出前扫一遍。契约段出现清单式罗列（多个人名 / 地名 / 术语 / 禁令并列）即重写。
- **不要求执行者声明合规**。自检只查格式（可解析、条目数、无残留）与显式语义项；不要求声明「术语全部对齐」之类，声明会诱发虚假自信，合规验证由编排者执行。
- **不设自检段**。任务卡不向执行者布置任何形式的自检（含格式核对与语义声明）——自检指令会诱导执行者写脚本或做超范围的逐项比对（脚本繁殖）。格式、术语、语义三查全部由编排者执行，执行者只做「读输入 → 写输出 → 交卷」。
- **输出段必须含落盘指令**（「把产出实际写入文件 + 读回确认」）。缺此指令时产出会停留在报告里而不落盘：报告含完整 JSON、看似完成，盘面却零文件。

## 5. 体量控制

巨大任务会拖死子代理：上下文膨胀叠加检查循环，表现为反复检查不落笔、超时、中止且无产出。派单前按体量拆分：

- **单实例体量上限**（经验值，按复杂度调节）：直做类 ≤2 批 / 实例、单批 ≤50 条（约 ≤100 行对白）；审计 / 分析类 3~5 批或 ≤200 行。上限随任务体量增大而收紧，体量越大完成率越低；渠道连续失败窗口期再减半。
- **按复杂度切，不按行数机械切**：高语义密度、长程依赖的连续内容，批数减半；模板化低风险内容可到上限。
- **续派是新的派单**：每轮续派同样守体量上限；同一实例累计续派不超过 3 轮。上下文叠加会稀释注意力、诱发漂移；跨工作段一律关旧开新。
- **失败即拆半**：实例中止且任务价值仍在时，把原任务拆成一半体量重派，不原样重试。生成被中途截断（读入完成、思考中断、无产出）尤其如此——同量重试必再触发。
- **大文本按字符权重拆分（工具化）**：单批源文 >10000 字符（如书籍正文）时按字符数而非条数拆——一条长文本抵一个小批次。用 `translation-batch-ops` 的 `shard_batch.py split/merge`，不手写脚本。

## 6. 并行协作纪律

**共享资源单写者**：任何「唯一真相」产物（最终文件、状态库、发布物）只允许编排者写。子代理只产中间文件（映射、补丁、报告），由编排者统一验收后应用。多写者并发会互相覆盖、丢更新。

**工作段分配**：并行实例尽量分配互不依赖的工作段；同一连续工作段给同一实例，跨段新建。

**命名空间隔离**：多路并行共用的中间产物，命名必须带任务标识；裸序号会被覆盖。

**幂等保护**：重跑与收口不得让过期产物覆盖已有修正；「已处理」条目的默认语义是跳过，除非显式要求重做。

**对账在先**：接手另一路写过的产物前，先核对基线（哈希 / 计数）；不一致先查明原因再动手。

**送达纪律（唯一触发）**：派单后不提前读取产出、不预验收、不预处理。产出的唯一处理触发是结果通知到达。提前处理的故障链：提前读 → 过早开始工作 → 报告在队列堆积 → 正式到达时被误判为「延迟」或「重复」。派单后尽快结束输出，让通知通道畅通。

**实例生命周期**：默认 派单 → 交卷 → 验收 → 关闭。仅当下一任务是同一连续工作段、需要沿用记忆时续接。关闭前确认实例没有「已交卷未送达」的产出。顺序：交卷 → 送达 → 消费 → 关闭。产出已落盘时才允许人工恢复，且那只属于故障恢复，不是常规路径。

**空位即派**：只要还有可派工作且有空闲实例位，立即派出去再等。空闲等待是吞吐浪费；「等」与「派」不矛盾：先填满池子，再等通知。**「已交卷待送达」的位算空闲**：交卷的位、刚验收完的位、刚关闭的位，凡有空闲立即补派（同连续段续派、否则新建）——补派不受“送达未到”限制，也不会影响前一次结果的送达；只有「关闭」必须等送达（防丢结果），别把「等送达」当「不能补派」的理由。

**角色位是职能覆盖，不是资源槽位**：检查空闲位时除了看“哪个实例闲了”，还要看“哪个职能位空缺”（如语感型助手位长期无任务时，优先把适配批次派给它而非再建同类分身），申报“本位置空闲”之前先确认真的没有适配批次。

**等 / 不等判据**：

- 有实例在途 → 等（收敛）：期间只做与在途工作不冲突的轻量准备。
- 无在途且有余量 → 立即开下一轮（发散）：备料、派单、继续推进。
- 合法停下的条件只有三种：可派工作枯竭、硬阻断（门禁拦截 / 待外部裁决）、用户或发起方叫停。「无在途任务，静候指令」不是合法收尾。

**串行资源**：单实例服务（本地模型、单线程 API）一次只跑一路。编排者亲自跑耗时任务时小口推进（每段 1~2 批），保持对结果通知的响应能力。

### 审计任务卡：最小闭环落盘纪律（硬规则，防超时分发散）

审计类子代理的典型失败模式不是能力不足，是**动作面无限发散**：逐条考证（全库翻查词族、跨批溯源）无限延长检查阶段，产出始终不落盘，直到超时/中断归零。审计任务卡必须包含以下三段，缺一不可：

1. **先建报告骨架（开工第一动作）**：动笔前先把报告文件骨架写到磁盘上（meta + 空数组 + summary 占位），每完成一个核查单元立即更新落盘，不得攒到最后一次性写。部分落盘 + 超时 = 仍有可用产出；全部在内存 = 归零。
2. **批内闭环，跨批禁止**：审计范围 = 任务卡指定的批次集合内逐行核查；发现需要跨批/全库对照的疑点，不检索、不考证，直接在该条问题里标注「需跨批核对」并给低/中建议——跨批考证是编排者的事。检索预算：单实例全任务的全文检索次数上限个位数，超出即视为发散信号。
3. **体量与交付时限自判**：审计行数 × 核查遍数应在实例单次运行时限内可完成（按经验上限 ≤5 批 / ≤120 行一次派单）；行数超限派单时就拆，不指望执行者自查。任务卡末尾固定一句：「若接近时限仍未完成全部核查，立即把已完成部分写入报告并交卷，宁可报不完不报零。」

验收侧配套：收到审计 aborted/超时时，第一步检查报告文件是否已有骨架/部分产出（部分产出仍可消费），再拆半重派剩余范围；重派任务卡必须含上三段。

### 项目并行工作流（翻译推进角色位）

翻译推进的五个角色位：**① 主助手分身直翻（至少 2 路）② 语感型助手直翻 ③ 结构化助手独立审查 ④ 编排者验收/裁决/唯一产物写回 ⑤ 本地模型（仅批量简单内容）**。角色位只描述分工模式；具体有哪些 agent 可用、各自能力定位，以当地环境实际提供的清单为准，不预设固定名单。

**角色位规则：满载是结果不是目标——只派真实必要任务，禁止为凑位而发明任务。** 每轮收口后检查各角色位是否有真实必要任务（存在待译批次/待审写回、且该位适配）：有则补派，没有就明确说「无必要任务，本位置空闲」，不得把低价值内容硬拆硬派或降低质量标准凑数——「为调度 KPI 而派单」与「该派不派」同为违规。

- **取批规则**：各子代理取不同任务段，避免同段上下文互相依赖与术语口吻漂移；同一任务段的批尽量给同一路连续做（续派），跨段新开实例。
- **审查对象**：独立审查审的是**已写回唯一产出**的批次（语义/语气/术语/世界观四查），问题以结构化 JSON 落盘，编排者确认后统一修，不让审查者直接改唯一产物。
- **本地模型按内容分派（批量苦力，不做复杂对白）**：适合规模大、结构简单、语义风险低的内容——模板化文本、格式化条目、重复结构段落、纯名录/清单类；角色语气/语境判断/术语敏感内容不交给它（繁体混出、英文残留、漏行等返工率高）。
- **本地模型小口吃（仅后备时）**：确需编排者跑本地模型时每段最多推 1~2 批，跑完立即回到「检查交卷 → 验收 → 续派/补位」循环，不在实例在途时连续推 3 批以上——长调用会锁住编排者，结果通知与验收全部滞后。

## 7. 产出验收（三查）

产出验收不能只看格式，也不能只看报告。

1. **结构查**：产物可解析；**键集合与输入键集合严格相等**（不是子集、不是数量相等）。键错位使产物与源错配，比内容错误更严重：重合率过低即整批不可用，不逐条修补。
2. **契约查**：对词表 / 规范逐条核。不听报告，扫实词：报告声称「已对齐」与产物实际形态可能相反；抽查重点放在「声称对齐」之处。
3. **语义查**：通读抽查关键条目（语气、指代、语境、否定）。字面直译与指代错误是典型目标。
4. **信息源核查（固定项）**：抽查子代理报告引用的信息源真实存在：任务卡声称的文件与字段是否真实、是否出现无依据的自造内容。任务卡下发错误信息时，执行者会补全世界，这是幻觉的入口。

修正完成后与唯一产物逐条对账，差异只允许是主动修正处。

**机械部分交给脚本**：键集合、格式、占位符、残留、计数的核查由确定性脚本执行，默认只读；修复走固定工具，不手工拼命令。语义判断才交给人或模型。

## 8. 故障归因与恢复

实例失败 / 中止 / 超时无产出时，**第一步读它的执行轨迹**（会话记录）还原：读了什么、走到哪、最后动作是什么。没有轨迹证据之前，不归因「模型不行」或「环境故障」。

| 归因         | 证据形态                                   | 对策                   |
| ------------ | ------------------------------------------ | ---------------------- |
| 任务设计问题 | 体量过大、输入缺失、键来源未说明           | 修任务卡，拆小重派     |
| 提示词问题   | 规则堆叠致过度谨慎、负向施压、关键约束缺失 | 按信息三分法重写任务卡 |
| 模型行为问题 | 反复检查不落笔、循环空转、自造格式         | 换执行者或换模板       |
| 环境故障     | 无执行痕迹即中断                           | 允许一次简单重试       |

恢复原则：任务价值仍在 → 拆小重派（大任务一次崩的概率高于小任务）；价值已被其他路径覆盖 → 不重派。生成中途截断（读入与思考已完成、无产出）属任务设计侧：减量重派、卡片强化生成纪律句（模板固定句之三）；同量原样重试必再触发（高发诱因：长考、复述清单、收尾自我修复）。归因结论回填任务卡模板：缺的约束补进模板，防止同一缺陷在下一个实例复发。

## 9. 编排者的例行事务

- 只做协调、验收、裁决、应用，不亲自跑重活；重活留给实例。
- 每轮收口核对阵容：每个可并行的角色位是否有**真实必要任务**；有则补派，没有就明说「无必要任务」。不为满足满载而发明任务，也不做「无在途任务，静候指令」式停摆。
- 每轮收口做幂等验证：重跑应表现为近零变更；批量变更说明盘面被动过，先对账。
- 进度汇报以确定性统计为准（脚本产出、计数、清单），不凭记忆报数；汇报保持轻量：进度 + 验收结论 + 阵容核对结果。
